# Dev observability UX: dashboards-as-code, provisioned alerting, span-derived metrics, and an in-cluster load generator

ADR-0009 stands up the LGTM backends and the three signals; every service now emits them. This ADR is the **UX layer** on top — turning three datasource islands into one navigable pane, and giving the dev cluster enough life that dashboards and alerts mean something. All of it is provisioned **as code** and rides the existing single-gateway-collector OTLP topology. The scope is a maximalist _teaching_ artifact: the dashboards and alert rules are themselves the lesson, so they live in the repo, readable and diffable, not in a pod's sqlite.

Five parts:

- **Dashboards as code, authored in TypeScript.** Boards are built with `@grafana/grafana-foundation-sdk` (Grafana Labs' official typed builder), synthesized to JSON, and mounted into Grafana via a dashboard-provider ConfigMap (`/etc/grafana/provisioning/dashboards`) alongside the existing datasource provisioning. No PVC — the pod stays stateless and re-provisions identically on every boot; UI edits are allowed but ephemeral, and surviving an edit means exporting it back to a TS definition in the repo (a deliberate "commit your work" step). The set: a **Services (RED)** folder (edge + auth, auth deep-dive), a **Domain** folder (the reservation-saga funnel, money & inventory, the expiration worker), and a **Platform / o11y** folder (the backends watching themselves). A `redRow(service, op)` factory keeps the six structurally-identical RED panels as one reviewed function instead of six drifting JSON blobs.
- **Correlation links.** Provisioned in the datasource `jsonData`: Tempo→Loki (`tracesToLogsV2`, `filterByTraceID`), Loki→Tempo (derived fields extracting `trace_id`), and Tempo→Prometheus (`tracesToMetrics`). All three work against what the services already emit — logs carry `trace_id`/`span_id`, spans carry `service.name`/`op`. This is the trace↔logs↔metrics triangle ADR-0009 sells but never wired.
- **Span-derived metrics + service graph.** The `dev` collector moves core→contrib to run the `spanmetrics` + `servicegraph` connectors, feeding the existing `otlphttp/prometheus` exporter (no Prometheus or Tempo change). This supplies RED for the services with only counters (tickets/orders/payments lack duration histograms) and the auto microservice-topology map (Grafana's Service Graph tab, via the Tempo datasource `serviceMap` → Prometheus). Runs **alongside** the explicit `Effect.Metric` series, not instead — see the ADR-0009 2026-06 update.
- **Alerting + SLOs.** Prometheus recording rules pre-aggregate the RED series (per-service error ratio, p95, saga conversion ratios); Grafana-managed alert rules provisioned as code cover SLO multi-window burn-rate (gateway/auth error ratio), saga stall, conflict/duplicate-publish spikes, and backend-down. Alerts route to a **webhook contact point → an in-cluster log sink**, so a firing alert is visible via `kubectl logs` — the full notification path, self-contained, no external account.
- **k6 load generator.** An in-cluster `Deployment` + script ConfigMap (no new pnpm workspace, no image to build/`kind load`) driving the gateway's public surface — sign-in, browse, reserve, pay — at a steady baseline with periodic induced failures (forced reservation races, payment declines) so the burn-rate alerts have something to trip on. k6's own load metrics flow `k6 → otel-collector → Prometheus` over the experimental OTLP output, on the same path everything else uses. Gated by a Pulumi config flag so it is **dev-only** and `prod` never gets it.

## Why dashboards as TypeScript rather than raw JSON or jsonnet

Raw Grafana JSON is huge and hand-hostile, and a metric rename means grepping JSON; jsonnet is powerful but drags a non-TS toolchain into a repo that has deliberately standardized on TypeScript (tsgo, tsdown, vitest-tested Pulumi manifests). The foundation SDK slots into exactly that pipeline — type-checked PromQL targets, reusable panel factories, and dashboard definitions that are readable code naming the metrics. The cost is one dependency and a synth step, both idiomatic next to the existing manifest synthesis.

## Why as-code with no PVC rather than UI-built boards

A PVC lets users build and save boards live, but the result is invisible to the repo, untestable, and lost on PVC delete. For a teaching artifact the boards _are_ the lesson and must be diffable; the stateless-pod property (every clone gets the identical curated stack, re-provisioned cleanly on every boot) is worth more than persistent UI edits. The friction — exporting a UI-crafted board back to a TS definition to keep it — is the right friction here.

## Why a load generator at all, and why k6

Alerts and SLOs against a silent cluster are theater: dead rules that never fire are worse than no rules. A continuous load makes every board alive and lets burn-rate alerts trip on demand. k6 over a bespoke TS loadgen workspace: it is Grafana Labs' own tool (on-brand for a Grafana-themed teaching artifact), adds zero build-graph weight, rides the existing OTLP metrics path, and yields a bonus load-profile dashboard for free. The downside — the script hits raw gateway HTTP and can drift from the arktype contracts — is small (it touches only the stable public surface) and self-announcing (drift surfaces as failed requests, a useful canary). A typed `apps/loadgen` reusing `@tix/contracts` was the alternative; it buys schema-alignment at the price of another workspace, Dockerfile, and smoke image, which is not worth it for dev scaffolding.

## Why span-derived metrics in the collector rather than Tempo's metrics-generator

Both synthesize RED + service-graph metrics. The collector connectors keep all signal-shaping at the single gateway collector (the design's center of gravity), do not reverse Tempo's deliberate "metrics_generator omitted" decision, and need no new Prometheus remote-write receiver — they ride the metrics pipeline that already exists. The cost is a bigger collector image (core→contrib), hidden because the smoke already pre-pulls the observability images in the background.

## Consequences

- `GrafanaBackend` grows a dashboard-provider ConfigMap and an alerting-provision ConfigMap; the datasource ConfigMap grows the three correlation links. `@grafana/grafana-foundation-sdk` is a new dependency, and a synth step renders TS dashboard definitions to the mounted JSON. All of it stays unit-testable the way `grafana-backend.test.ts` already asserts on rendered manifests.
- The collector image moves core→contrib; the collector config gains the `spanmetrics` + `servicegraph` connectors and a metrics-pipeline branch. The smoke's pre-pull list must include the contrib tag.
- A new dev-only k6 `Deployment` + script ConfigMap and a log-sink contact-point target join the topology, both behind a Pulumi config flag that is off for `prod`.
- **Exemplars — spike resolved (2026-06): not on the hand-rolled metrics, yes on the span-derived ones.** `@effect/opentelemetry@0.63.0`'s `OtlpMetrics` builds every data point from `Metric.unsafeSnapshot()` — a polled, process-global aggregate (`count`/`sum`/`bucketCounts`/`explicitBounds`) — and never reads a span context or sets the OTLP `exemplars` field. This is architectural to Effect's `MetricRegistry`, not a config gap, so the **hand-rolled `Effect.Metric` histograms cannot carry exemplars** without an upstream change. The metric→trace jump is instead delivered on the **`spanmetrics`-derived `duration` histograms** via the connector's `exemplars.enabled: true` (it has the trace ID because it derives from spans). So we still wire `exemplarTraceIdDestinations` → Tempo + `--enable-feature=exemplar-storage` on Prometheus, but the exemplar-bearing series are the span-derived RED histograms, and dashboards should drill-to-trace from those, not from `order_value_cents`/`payment_charge_latency_ms`/`*_duration_ms`.
- We now run two parallel metric systems (explicit + span-derived). Dashboards must label which series is which so the saga funnel does not double-count `orders_created_total` against `calls_total{service="orders"}`.
- **Load generator landed (2026-06).** `LoadGenerator` (`infra/pulumi/components/load-generator.ts`) is a dev-only `grafana/k6` Deployment + script ConfigMap, gated by the `loadgenEnabled` Pulumi flag (on in `dev`, unset in `prod`). The script drives the gateway's public surface as raw HTTP — better-auth sign-in over the `/api/auth/*` proxy (bearer token from the `Set-Auth-Token` header), then `POST /rpc/<seg>/<seg>` with body `{"json": <input>}` for browse/reserve/pay — and induces reservation races (concurrent reserves on a hot ticket) and payment declines (`pm_card_chargeDeclined`). k6's own metrics ride the experimental OTLP output to the collector → Prometheus; the `load-profile` board (Platform folder) renders them. The pay stage needs a real Stripe `sk_test_…` key to clear; the script otherwise holds literal `/rpc` paths + arktype field names (the accepted drift risk — drift surfaces as failed checks).
- **Remaining boards + redRow landed (2026-06).** The Services (RED) folder (edge+auth, auth
  deep-dive), the Domain money & inventory + expiration-worker boards, and the Platform/o11y
  board are all provisioned as-code. The six gateway/auth RED panels are one reviewed
  `redRow(service, { y, by })` factory (`dashboards/red-row.ts`) over the hand-rolled
  `<svc>_requests_total`/`_request_errors_total`/`_request_duration_ms` series, grouped by
  `op` — never the span-derived `calls_total`, so no panel double-counts. The Platform board
  shipped **with** its scrape plumbing rather than deferred: `prometheus-backend.ts` now
  carries `scrape_configs` for the LGTM backends (collector telemetry on `:8888`, Tempo
  `:3200`, Loki `:3100`, Prometheus self `:9090`, Garage admin `:3903`/metrics), the first
  scrape path in a stack that was OTLP-push-only. `up{job=~...}` is the version-stable
  liveness core; the ingest-rate panels are best-effort against the pinned images.
